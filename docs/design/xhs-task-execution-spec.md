# 小红书导入任务状态机与等待回答行为树规格

规格根据 2026-10-18 已确认的设计编写。实现方向与测试接口已确认，已发布为 [GitHub Issue #18](https://github.com/sunshanlu/openCook/issues/18)。框架适配与实现未开始。

## Problem Statement

小红书分类与提取需要在发送结果不明、页面异常、回答迟到、生成中断、校验失败和保存故障等情况下持续运行。当前多个层次维护地方性状态，用户难以确认任务停在哪里、何时能安全重试、重启后是否会重复发送或丢失回答。

用户希望流程阶段清晰，等待期间能够按现场条件采取动作，并且每次恢复都延续原任务、原请求及预算。一个访问账号的问题应按实际影响阻塞处理，已经收尾的预期失败可进入人工复核，未决请求则必须保留。

## Solution

为每条视频笔记的一次分类或提取建立持久化导入任务。采用 transitions 管理“准备、提交、等待、校验、保存、完成、待人工复核、阻塞”，等待阶段由 py_trees 组织观察、恢复和异常处理。框架组合先通过适配验证，再实施替换。

用户能够看到当前阶段、等待或阻塞原因、尝试次数和下次检查时间。重启后继续原任务，提交不明时先核对，保存失败时只重试保存。分类和提取继续独立执行；分类判定为教程后可靠生成提取任务。

## User Stories

1. As an 导入操作者, I want 每个视频的分类和提取成为独立导入任务, so that 两种工作可以分别恢复和跟踪。
2. As an 导入操作者, I want 教程分类成功后生成提取任务, so that 提取无需人工交接且不会漏入队。
3. As an 导入操作者, I want 明确看到准备、提交、等待、校验和保存阶段, so that 我能判断任务进度。
4. As an 导入操作者, I want 发送前保存点点请求身份和发送意图, so that 意外退出后仍能核对提交。
5. As an 导入操作者, I want 提交结果不明时先查原会话, so that 不会重复发送同一个请求。
6. As an 导入操作者, I want 回答与正确的视频和请求关联, so that 其他对话的内容不会混入菜谱。
7. As an 导入操作者, I want 仅接收已结束且稳定的完整回答, so that 生成中的部分内容不会入库。
8. As an 导入操作者, I want 超时后继续有限观察迟到回答, so that 已完成的点点交互不会被浪费。
9. As an 导入操作者, I want 完整回答优先于超时判断, so that 边界时刻出现的回答仍能被接收。
10. As an 导入操作者, I want 明确空回答和中断有单独处理规则, so that 页面不可读不会被误当成回答为空。
11. As an 导入操作者, I want 页面恢复围绕原请求进行, so that 刷新和恢复不会产生新提交。
12. As an 导入操作者, I want 页面恢复与点点请求分别计数, so that 我能理解实际请求成本。
13. As an 导入操作者, I want 重新请求保留旧尝试并使用新请求身份, so that 迟到回答仍有核对依据。
14. As an 导入操作者, I want 回答原文在校验前保存, so that 校验失败也能审查原始结果。
15. As an 导入操作者, I want 校验归属、结构、必需字段和可检测矛盾, so that 不合格结果不会被当成成功。
16. As an 导入操作者, I want 程序不自动补全缺失菜谱内容, so that 自动处理不会编造食材或步骤。
17. As an 导入操作者, I want 已结束的无效结果在预算内重试、耗尽后复核, so that 常见失败可以有明确结论。
18. As an 导入操作者, I want 未决请求即使预算耗尽也保留为阻塞, so that 程序不会遗失仍在进行的请求。
19. As an 导入操作者, I want 入库与完成标记原子提交, so that 退出恢复不会重复插入结果。
20. As an 导入操作者, I want 分类结果与提取入队原子提交, so that 不会出现完成分类但漏提取或重复入队。
21. As an 导入操作者, I want 保存失败只重试保存已有结果, so that 不会再次消耗点点请求。
22. As an 导入操作者, I want 暂停和重启保留次数、期限及恢复位置, so that 重启不会绕过预算。
23. As an 导入操作者, I want 登录或验证码只阻塞对应访问账号的处理, so that 另一访问账号可以继续已有工作。
24. As an 导入操作者, I want 共享数据库故障阻塞整个批次, so that 所有执行者都停止不可靠推进。
25. As an 导入操作者, I want 暂时故障自动检查而身份冲突等待人工裁决, so that 恢复方式与风险相符。
26. As an 导入操作者, I want 人工等待不消耗自动处理预算, so that 处理验证码的时间不会耗尽任务执行预算。
27. As an 导入操作者, I want 恢复后先核对原请求再判断期限, so that 人工等待期间产生的回答不会被遗漏。
28. As an 导入操作者, I want 清楚看到为何等待、重试或阻塞, so that 可以依据记录处理问题。
29. As an 导入操作者, I want 固定行为树只开放经过验证的参数, so that 配置不能绕过请求归属和安全重试规则。
30. As an 导入操作者, I want 新执行器经过故障验证和少量真实任务验证再切换, so that 现有未决请求不会受到未经验证的改造影响。
31. As an 导入操作者, I want 菜谱抽样对照原视频, so that 结构合法之外的忠实性和完整性也被检验。
32. As an 维护者, I want 本地观察动作可中断且心跳持续响应, so that 长等待不会被监督层误认为失联。
33. As an 维护者, I want 同一任务只有一个控制者和执行者, so that 并发事件不会重复推进或重复发送。

## Implementation Decisions

- 第一版改造单任务执行器，保留分类／提取双 worker、不同访问账号和提取队列；协调器仅进行结果及阻塞范围所需适配。
- 新执行器唯一推进任务阶段。现有 ChatSession 的发送、会话恢复、核对能力复用，其重试及阶段推进控制权迁移，不能与新逻辑同时控制任务。
- 优先采用 transitions 与 py_trees；不自建执行机制。实施先验证同步／异步适配、事件串行、非阻塞 tick、生命周期终止和恢复，再锁定版本。
- 任务阶段与请求事实、行为树进度分别记录。任务身份跨尝试保持稳定，新提交创建新请求身份，旧请求保留。
- 正常阶段为准备任务、提交请求、等待回答、校验回答、保存结果、完成；另有待人工复核与阻塞。暂停为独立运行控制。
- 提交阶段保存意图并确认提交，结果不明先核对；恢复提交阶段遵循相同规则。确认未提交才允许重新发送。
- 行为树固定结构，按身份冲突、页面可用性、请求关联、完整回答、异常回答、超时、继续观察的优先级执行。
- 每次决策使用带时间的观察快照，页面改变后重新观察。选中分支内的动作失败必须在该分支处理，不能落入低优先级动作。
- 条件与动作通过框架生命周期执行；有副作用的动作只启动一次，后续 tick 推进。终止本地观察不证明远端生成结束。
- 树的业务结果独立于节点状态：运行中、回答就绪、需要重试、需要复核、阻塞。结束出口只交付一次结果，由状态机检查转移。
- 页面不可读不能证明未登录、空回答或未提交。完整回答必须唯一关联原请求、有结束证据并满足稳定观察。
- 正常等待 180 秒，延长观察 600 秒；完整回答稳定确认 1 秒、空回答 5 秒，均需明确结束证据。
- 每任务点点请求上限 2 次；页面恢复上限 6 次，第 3 次失败后退避 300 秒；保存失败最多重试 3 次，短暂退避后仍失败则阻塞。
- 自动处理总预算 35 分钟，累计自动动作、观察和自动退避；人工等待暂停累计。真实回答期限及次数不因暂停或重启重置。
- 轮询间隔、短退避、核对单次期限及最终稳定观察的具体工程参数在适配中确定，必须有限、记录并受总预算约束。
- 自动预算边界先核对，仍遵守访问权限与冻结规则；无法核对则保留未决身份并阻塞。预算耗尽不启动新请求。
- 页面恢复、点点请求与保存分别计数。可能已发出的请求保留额度占用，核对后结算；继续遵守现有发送／访问额度、爬坡、冻结和每日运行窗口决策。
- 校验严格检查归属、结构、字段类型、必需字段与可检测业务矛盾。归属冲突阻塞；其他不合格在原请求结束后预算内重新请求，耗尽后复核。不加入自动补全或纠正对话路径。
- 持久化检查点包括发送意图与额度占用、提交关联身份、完整回答原文与证据、结构化结果与校验版本、结果与完成标记。
- 业务结果与任务完成原子提交，分类判定教程时同一事务生成提取队列项。使用稳定任务身份保证重复执行不会重复结果或入队。
- 数据记录需要表达阶段、恢复阶段、尝试／请求关系、预算、期限、阻塞原因与范围及校验版本；具体 schema 和唯一约束由实施设计确定，并兼容既有请求事实。
- 阻塞按任务、对应 worker、整个批次分级。共享存储故障及无法界定影响的不变量破坏阻塞整个批次。
- 可验证暂时故障自动退避检查；登录／验证由用户处理后检测；身份冲突和证据矛盾须人工裁决。
- 恢复从 SQLite 和请求证据重建框架执行，不序列化框架实例，不重置预算。复核记录保存成功才允许批量调度推进，未决阻塞任务不被跳过。
- 关键日志记录任务／请求身份、转移、事件、分支、依据、预算及恢复位置；变化时记录决策，心跳独立。原文与诊断证据分开引用，沿用脱敏与保留约束。
- 不自动迁移历史未决请求；少量新任务验证后，另行受控切换，旧请求由旧逻辑收尾或人工核对。同一任务只能有一个执行者。

## Testing Decisions

- 已确认主要测试 seam 为单任务执行器对调用者的外部接口：输入分类／提取任务及可替换的浏览器、存储、时钟依赖，观察持久化结论、外部调用及恢复行为。具体方法名待实施确定。
- 优先沿用现有 Workflow／ChatSession 的调用位置和浏览器、Store、时钟测试替身，不要求调用者跨越多个新接口。
- 测试外部行为和持久化约束，不断言树节点布局、框架私有字段或回调次数来镜像实现。
- 核心任务执行、等待行为、校验和保存通过该最高测试 seam 集成验证；并行账号阻塞范围另在既有协调器 seam 验证。
- 复用现有聊天、浏览器、页面访问状态、节流、运行时和并行协调测试中的原请求核对、恢复持久化、时间推进与任务认领先例。
- 验证发送后确认前退出恢复先核对、没有盲目重发；唯一归属失败则阻塞。
- 验证期限边界及延长期迟到回答优先接收，不创建新请求。
- 验证多次页面恢复不丢身份、不消耗请求次数，动作失败不落入低优先级分支。
- 验证校验失败保留原文、原请求收尾后才重试；耗尽的未决请求阻塞而非复核。
- 验证事务成功返回前退出后不重复插入、不重复入队，保存重试不重新请求点点。
- 验证暂停、重启和人工恢复不重置预算／期限，并先核对原请求。
- 验证单账号阻塞时另一个继续，共享存储故障阻塞整个批次。
- 验证非阻塞 tick、心跳响应及本地中断，不把本地取消作为远端结束证据。
- 模拟故障通过后，以少量新真实任务检验页面适配、请求关联及正常分类／提取；抽样对照视频检验菜谱忠实性和完整性。

## Out of Scope

- 本规格发布不包含立即实现、启动任务或切换生产执行器。
- 自建状态机／行为树引擎、自由编辑树结构、动态节点加载和运行中热更新。
- 全面重做批量调度、账号绑定、节流和监督系统。
- 自动迁移历史未决请求、双执行器同时接管任务、清除原请求证据。
- 自动补全缺失菜谱内容、额外格式纠正对话、以结构合法宣称内容完整。
- 绕过访问账号冻结、运行窗口、安全审批或请求身份约束。
- 自动合并 PR 或手动关闭 Issue。

## Delivery Contract

没有既有 Agent Brief 或源 Issue 的 Delivery Contract。采用默认交付：创建或复用专用 typed branch（遵守项目 codex/ 分支前缀），完成实现、提交并审查，随后推送并创建或更新 draft PR，其描述默认包含 `Closes #<issue-id>`。处理审查问题后标记 ready for review。不合并，不手动关闭 Issue。

这约束后续实现交付，不表示本次规格发布会修改业务代码或启动生产任务。实际生产切换另行授权并遵守状态保存与未决请求核对流程。

## Further Notes

已确认方案以 ADR 0003、现有访问节流及导入会话保留决策为约束。未决请求或恢复依赖仍阻止清理相关导入会话。

框架适配失败时调整接入方式并报告证据；不得未经验证声称框架组合已经可用，也不静默改回自建引擎。

拟发布到项目 GitHub tracker，应用 ready-for-agent 标签。测试 seam 已确认；工单拆分须先完成 to-tickets 预览批准及项目 tracker 关系约定核对。
